Ibexa TypeScript Config

## Generating aliases for project repository
From project repository run with optional arguments:
```node node_modules/@ibexa/ts-config/scripts/generate-aliases.mjs```

### Available arguments
`--project-path` - if run from other place than DXP installation or bundle with installed vendors
`--design-system-path` - absolute path to Design System repository, only needed in dev environment if you're working on DS components
`--tsconfig-filename` - allows to generate aliases to file different than `tsconfig.json`
`--relative-to` - required, has three options:

#### project
Creates aliases relative to project directory (`cwd` or `--project-path`)

#### bundle
Creates aliases relative to current bundle directory (like `vendor/ibexa/admin-ui`)

#### custom
Used with `--custom-relative-path` argument, it creates aliases relative to path from this argument

## Generated files

`yarn ibexa-generate-tsconfig` (run by `yarn install` in every bundle and by the Composer scripts of a project) decides what to write from where it runs:

- **project root** (the directory holds `webpack.config.js`): the full config with every alias and `typeRoots` goes to `tsconfig.ibexa.json`. A `tsconfig.json` is created next to it only when there is none, as a solution file with `"files": []` and a project reference to `./tsconfig.ibexa.json`; an existing `tsconfig.json` is never touched (see [A project's own TypeScript](#a-projects-own-typescript));
- **bundle inside a project** (no `webpack.config.js` in the bundle, but one in a parent directory, for example `vendor/ibexa/admin-ui`): `tsconfig.json` extending the project's `tsconfig.ibexa.json`. The project file has to exist, otherwise the run stops with an error pointing at the project;
- **standalone bundle** (no project root above, including a checkout symlinked into a project's `vendor/ibexa/`): `tsconfig.json` extending `@ibexa/ts-config` directly, with the aliases of the bundle's own `vendor/ibexa/`.

`tsconfig.ibexa.json` and a bundle's `tsconfig.json` start with a `// Generated by @ibexa/ts-config` comment and are overwritten on every run: there is nothing to edit there by hand, and nothing to commit. The project's `tsconfig.json` has no such comment because it belongs to the project.

Projects whose root `tsconfig.json` was written by an older generator (the full config without the comment, or the two-line file extending `tsconfig.ibexa.json`) keep using that stale file; delete it once and let the next run create the solution file.

## What the Ibexa config contains

`tsconfig.ibexa.json` (and the `tsconfig.json` of a standalone bundle) describes one TypeScript program: the sources of the Ibexa bundles, typed against the packages those bundles run with. Those packages are the ones shipped by `ibexa/admin-ui-assets` and `ibexa/headless-assets`, not whatever the project happens to have in its own `node_modules`:

- `include` covers `vendor/ibexa/*/src/bundle/**/*` only; configuration files, tests and fixtures at the bundle root stay out of the program;
- `paths` maps every Encore alias of the bundles, plus `react`, `react-dom` and `csstype`, to the copies of their type declarations in `admin-ui-assets` (`csstype` to the one next to them in `node_modules`, until `admin-ui-assets` ships it). This is what the admin UI runs on (`window.React` comes from `admin-ui-assets`), so the types follow the runtime, and the project is free to use another React version for its own code;
- `typeRoots` points at the `@types` directory of `admin-ui-assets`, which is where `bootstrap`, `leaflet` and the other declarations only shipped there are found;
- `types` is empty, so nothing from any `@types` directory is added to the program on its own. Everything enters through an import, which keeps a package from being loaded twice from two directories; a second copy of `@types/react` is enough to crash `ts-loader`.

## A project's own TypeScript

The generated `tsconfig.json` at the project root is a solution file: it holds no options and lists the projects below it, so an editor opens every file from `vendor/ibexa` with `tsconfig.ibexa.json` (or with the bundle's own generated `tsconfig.json` when there is one). A project that has TypeScript of its own adds a second project next to it and references it from the solution file:

```json
{
    "files": [],
    "references": [
        { "path": "./tsconfig.ibexa.json" },
        { "path": "./tsconfig.app.json" }
    ]
}
```

```json
{
    "extends": "@ibexa/ts-config",
    "include": ["assets/**/*"],
    "exclude": ["node_modules", "public", "vendor"],
    "compilerOptions": {
        "typeRoots": ["./node_modules/@types"]
    }
}
```

`tsconfig.app.json` is the project's file: it types `assets/` with the packages from the project's `node_modules` and knows nothing about the Ibexa bundles. Extending `tsconfig.ibexa.json` from it instead would pull the aliases and the `react` mapping of the admin UI into the project's code, which is rarely what a project wants.

## Assets packages in a standalone bundle

The global declarations of the Ibexa bundles reach into sources that import the npm packages shipped by `ibexa/admin-ui-assets` and `ibexa/headless-assets` (for example `@ibexa/types` and `@ibexa/utils` used by page-builder). A standalone bundle checkout usually has neither in its `vendor/`, so `tsc` fails with `Cannot find module`.

When the generator runs in a standalone bundle checkout it makes sure both are available:

- `ibexa/admin-ui-assets` for every bundle,
- `ibexa/headless-assets` for every bundle with `"license": "proprietary"` in its `composer.json`.

The version is `dev-X.Y-next`, with `X.Y` taken from the bundle's `extra.branch-alias`. The packages are installed with Composer into a project of their own in `node_modules/.cache/ibexa-ts-config/assets/` and symlinked into `vendor/ibexa/`. The bundle's `composer.json` and `composer.lock` are not touched. The side project reuses the bundle's `repositories` and its `auth.json` when there is one, so the same credentials work as for `composer install`.

Every run refreshes that project with `composer update`, so `yarn install` always leaves the assets at the current state of their `-next` branch, the same way `composer install` without a lock file does for the bundle's own dependencies. When nothing changed this costs about a second. If the refresh fails, for example offline, the version installed before is used and a warning shows Composer's error; only a first install without network fails. A real package directory or a symlink made by something else in `vendor/ibexa/` is left alone. Removing `node_modules` removes the installed assets as well; the next `yarn install` brings them back.

## Generating API schema for TS
Download openapi.yaml
```wget https://raw.githubusercontent.com/ibexa/documentation-developer/refs/heads/5.0/docs/api/rest_api/rest_api_reference/openapi.yaml```

Due to current bug in openapi file parts of file that starts with `$ref: '#/components/examples` needs to be removed before generating .d.ts file.

Generate schema.d.ts file:
```npx openapi-typescript ./openapi.yaml -o ./types/schema.d.ts```
